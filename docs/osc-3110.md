# OSC ELLO protocol

OSC ELLO is TJ's private in-band protocol. `ELLO` is the mnemonic for the
numeric OSC code 3110. Shell plugins use it to attach
command context to an entry. Other terminal programs may use it to publish
resources or omit visible output from recording.

The protocol travels in the program-to-terminal byte stream. It does not use a
separate socket or file descriptor.

## Framing

Messages use this form:

```text
OSC ELLO ; MESSAGE ST
```

`ELLO` is written as `3110` on the wire. Message names are uppercase and
case-sensitive.

In bytes, `OSC` is `ESC ]` and `ST` is `ESC \`:

```sh
printf '\033]3110;MESSAGE\033\\'
```

ELLO messages end with `ST`.

Recognized TJ messages are removed before bytes reach the terminal or the
entry's `out` resource. `tjctl new --keep-osc` and `tjctl use --keep-osc`
forward them to the terminal for debugging, but still do not write them to
`out`.

OSC payloads are limited to 32 KiB. A confirmed TJ message that is malformed,
unsupported, oversized, or unterminated is dropped and reported in the bounded
journal log. OSC messages outside TJ's namespace pass through unchanged.

## Command context

Immediately before a command starts, the shell plugin emits:

```text
OSC ELLO ; CONTEXT ; PAYLOAD ST
```

`PAYLOAD` is standard base64 encoding of this byte sequence:

```text
1;<cmd-length>;<cwd-length>;<expanded-flag>;<expanded-length>;<cmd><cwd><expanded>
```

Lengths count bytes, not characters. `expanded-flag` is `0` or `1`; when it is
`0`, `expanded-length` must be zero. This length-prefixed envelope allows the
three values to contain arbitrary text without colliding with separators.

`CONTEXT` is normally emitted once per command by a shell plugin: from zsh's
`preexec` hook or Fish's `fish_preexec` event. It is a complete message, not an
output region, so it does not use `END`.

The context message does not start an entry by itself. The plugin follows it
with OSC 133 command-boundary messages. TJ uses the pending context when OSC
133 `C` starts the entry. See [Shell integration](shell-integration.md).

## Writer handoff

When `tj-new` or `tj-use` is run from a direct shell already managed by TJ, it
uses `tjctl` to emit a private request instead of starting a nested writer:

```text
OSC ELLO ; HANDOFF ; BASE64 ST
```

The payload is versioned, length-prefixed binary data containing the operation,
target journal, replay/title options, the writer's session token, and no shell
command. `tjctl` validates the target before emitting it; the active proxy
consumes it and moves recording to the target while the shell remains running.
It is emitted only by `tjctl`; programs should not use it. A failed target
selection leaves the source writer running.

The session token is a random value the proxy generates at startup and exports
as `TJ_SESSION_ID`. `tjctl` inherits it through the environment; bytes that
merely pass through the terminal - a displayed file, output from a remote
host - never see it. A handoff whose token does not match the active writer's
is dropped and noted in the journal log, without a reply: replacing the writer
is TJ-private control, not part of the public protocol.

## Save a temporary journal

`tjctl save` asks the active proxy to make its temporary journal persistent:

```text
OSC ELLO ; SAVE ; TOKEN ST
```

This is private TJ control protocol. `TOKEN` is the writer's `TJ_SESSION_ID`
session token, checked the same way HANDOFF's is; a bare or wrong-token SAVE
is dropped and noted in the journal log. The proxy removes the journal-local
temporary marker; shell code does not mutate the journal directly.

## Published resources

A program can expose a span of ordinary terminal output as a named entry
resource:

```text
OSC ELLO ; RESOURCE ; PATH [ ; MIME ] ST
RESOURCE BYTES
OSC ELLO ; END ST
```

For example:

```sh
printf '\033]3110;RESOURCE;files/data.csv;text/csv\033\\'
printf 'date,amount\n2026-08-01,12.50\n'
printf '\033]3110;END\033\\'
```

The user sees the CSV normally. TJ also exposes it as
`@ENTRY/files/data.csv`. The bytes remain part of `out`.

`RESOURCE` is typically emitted by a program that wants part of its terminal
output to remain addressable, or by `tj filter --fence`.
`END` is emitted by the same program or wrapper after the last resource byte.

The MIME type is optional. When omitted or empty, it defaults to
`application/octet-stream`.

An entry may publish at most 32 resources. Each published resource is capped
at 64 MiB; a resource that reaches the cap is marked truncated and recording
continues normally.

Resource paths are relative to the entry directory. TJ rejects empty paths,
absolute paths, `..`, and paths that replace core resources or private removal
metadata. Core reserved names include `cmd`, `cwd`, `out`, `prompt`, `rc`, and
`meta.json`.

TJ reverses the PTY's normal newline translation when writing a resource. This
restores the bytes emitted by ordinary text programs. Binary data is supported,
with two limits:

- Bytes equal to TJ's `END` marker close the region.
- Tab expansion performed by the terminal cannot be reversed.

## Noout regions

A noout region remains visible but is omitted from the entry's `out` resource:

```text
OSC ELLO ; NOOUT ST
VISIBLE BYTES
OSC ELLO ; END ST
```

At the start of the region, TJ writes `<tj:noout>` to `out` once without
displaying it. Bytes inside the region go to the terminal but not to `out` or a
published resource. Recording resumes after `END`.

The user-facing wrapper is:

```sh
tj filter --noout -- command args...
```

It runs the supplied argv directly and preserves its standard streams,
environment, working directory, terminal, exit status, and signal result. It
makes a best effort to emit `END` if the child is interrupted.

`NOOUT` is typically emitted by `tj filter --noout`, by TJ commands whose own reports
should not feed later history or searches (`hist`, `grep`, `du`, and `tui`), or
by a cooperating program with similarly temporary output. `END` is emitted
after that display is complete.

Noout is explicit. TJ does not infer it from the PTY ECHO flag. Password input
with echo disabled is already absent from terminal output, and many non-secret
programs also disable echo.

Noout flags or payload sizes are not stored in `meta.json`.

## Region rules

Published resources and noout share one region state:

- Regions do not nest.
- Only one resource or noout region may be open.
- If another `RESOURCE` or `NOOUT` arrives, the first region remains open.
- The generic `END` message closes either kind of region.
- An `END` without an open region is a protocol error.
- An unfinished resource is closed and marked truncated at the entry boundary.
- An unfinished noout region is cleared at the entry boundary without adding
  metadata.

These rules prevent an incomplete region from affecting the next entry.

The normative protocol and recording behavior are defined in
[TJ-spec.md](../TJ-spec.md).
